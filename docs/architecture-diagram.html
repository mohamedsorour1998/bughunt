System Architecture

System Shape — Built for 1M DAU

At 1M DAU × 5 games/day the system processes ~290 game resolves/second at peak. Every design decision below traces back to that number.

  • Vercel + Next.js 16 App Router — globally distributed edge for static/SSR; API routes as serverless functions. Stateless by design: any instance can handle any request. No servers to provision, patch, or scale.
  • DynamoDB single-table (bughunt-main, on-demand, Global Tables → 3 regions) is the source of truth for every entity: users, games, answers, bugs, daily challenges, tournaments, orgs, social graph, notifications, chat. On-demand capacity absorbs 290 resolves/s ≈ 3,500 WCU/s with no provisioning. UUID partition keys distribute writes uniformly — no hot partitions. TTL (expiresAt) auto-reaps stale data at no read cost.
  • DynamoDB Streams → Lambda leaderboard materializer — resolveGame stamps Elo audit fields on the GAME#id item; the Lambda moves RANK#<paddedElo>#<userId> rows under LEADERBOARD#GLOBAL. Top-100 read = one descending Query with Limit: 100. Constant time at any user count — no scan, no sort, no aggregation at read time.
  • Upstash Redis — ephemeral coordination only: Elo-bucketed matchmaking sorted sets (human vs human pairing by skill range), rate-limit counters, game-event pub/sub. Every consumer has a DynamoDB fallback — Redis failure degrades experience, never corrupts data.
  • Bedrock Nova Lite — community-bug quality gate, admin bug generation, and optional bot AI (reads code, picks answer within 2.5s timeout).
  • All concurrency settled by ConditionExpressions — double-submit, double-resolve, tournament join races, chat caps, follow edges, optimistic-versioned bug index. The loser of any race gets a clean no-op; no locks, no transactions, no corruption.

Why DynamoDB (and not SQL) for This Workload

Every hot-path access is a key lookup or a single-partition Query — no joins, no aggregations at read time:

Access PatternKeyCost
Load profileUSER#id / PROFILE1 RCU
Active game for userGSI1 ACTIVE_GAME#userId1 query

Writes are guarded by ConditionExpressions everywhere two requests can race (double-submit, double-resolve, join, chat caps, follow edges, tournament capacity, BUG#INDEX optimistic versioning with bounded retries).

Known Limits & Mitigation Paths

Limit 1 — Leaderboard Partition Write Rate

Every ranked resolve funnels up to 8 writes (2 players × 2 boards × delete+put) into the LEADERBOARD#GLOBAL partition. At ~1,000 WCU/partition/s, that caps at ≈125 resolves/s — roughly 0.4M DAU at 5× peak.

Mitigation: Lambda caches the top-100 cutoff Elo and skips writes for players below cutoff − 50. At million scale >99% of games involve no top-100 candidate, cutting partition traffic by two orders of magnitude. Fallback: shard boards by Elo band and fan-in the top query.

Limit 2 — BUG#INDEX Item Size

The bug catalog index is one item (~40B/id → ~10K bugs within the 400KB item cap; warn logs at 50%). Fine for a curated catalog.

Migration path: per-difficulty index items (the byDifficulty map is already the natural shard key) — five smaller items with the same optimistic-versioning write path.

Limit 3 — SSE on Serverless

Each active game holds a function open. When REDIS_URL is set, TCP pub/sub pushes events with a 10s safety poll, cutting per-game DynamoDB reads from 0.5/s to ~0.1/s. Without it, polling DynamoDB every 2s.

Either way: held-open functions are the costliest part dollar-wise (data-wise both modes scale). Final fallback is plain client polling — graceful degradation when both Redis modes are unavailable.

Limit 4 — Multi-Region Writes

Global Tables replicate bughunt-main to eu-west-1 and ap-southeast-1. Reads route to the nearest replica. Writes are pinned to us-east-1 while Vercel functions run single-region — flipping on multi-region functions makes writes local too.

Caveat we accept: DynamoDB conditional writes are evaluated per-region, so cross-region active-active would need region-pinned games (players matched through one global queue, so a game’s writes naturally share a region).

Failure-Mode Design

Redis down → matchmaking returns “waiting” (no crash), SSE falls back to DynamoDB polling, rate limiting fails open. No data loss.

Lambda down → games still resolve and profiles still update; the leaderboard goes stale and self-heals when the stream resumes (24h retention), or scripts/rebuild-leaderboard.ts rematerializes it from profiles.

Double-everything → (submit, resolve, join, rematch, bot turns) conditional writes make the second writer a no-op.
